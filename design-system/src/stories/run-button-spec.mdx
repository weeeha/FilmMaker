# Run Button

## Overview

The Run Button starts the execution of the current workflow or selected run
configuration. The component is available in two variants:

- **Single** — performs one immediate Run action.
- **Split** — provides an immediate Run action and a separate menu of related
  run options.

The Split variant is visually presented as one control but is programmatically
composed of two independent buttons. Each segment has its own click target,
focus, hover, pressed, and active states.

---

## Anatomy

### Single variant

1. Button container
2. `Run` label
3. Optional loading indicator

### Split variant

1. **Primary action** — starts the Run action.
2. **Divider** — visually separates the two interactive targets.
3. **Dropdown trigger** — opens a menu of related run options.
4. **Chevron icon** — indicates that additional options are available.
5. **Dropdown menu** — contains additional actions related to running the workflow.
6. **Loading indicator** — communicates that the primary Run action is in progress.

The divider is visual only and must not act as a separate interactive element.

## When to use

Use the **Single** variant when:

- There is one clear and predictable Run action.
- Users do not need to choose between additional run modes.
- Additional options are unavailable or unnecessary.

Use the **Split** variant when:

- There is a clear default Run action.
- The default action is the most frequently used option.
- Users occasionally need access to additional, closely related run actions.
- Hiding secondary actions helps reduce visual complexity.

The primary segment must always represent a safe and predictable default action.

---

## When not to use

Do not use the Split variant when:

- Users must select an option before every run.
- There is no meaningful default action.
- The menu contains unrelated actions.
- The menu contains complex settings, form fields, or configuration controls.
- The list of options is long or requires explanation.
- Clicking Run could produce an unexpected result because the current
  configuration is unclear.

If users must select a value before running, use a separate Select, Combobox,
Popover, or configuration panel followed by a Single Run Button.

If the dropdown contains complex interactive content, use a Popover or Dialog
instead of a menu.

---

## Interaction behavior

### Single variant

- Clicking Run immediately starts the workflow.
- `Enter` or `Space` activates the button when it has keyboard focus.
- The button does not open a menu.
- Focus normally remains on the button after activation unless the action moves
  the user into a new context.

### Split variant

The Split variant contains two independent interactive elements.

#### Primary Run action

- Clicking Run immediately starts the default Run action.
- It must not open or toggle the dropdown menu.
- It must not inherit the open state from the dropdown trigger.

#### Dropdown trigger

- Clicking the dropdown trigger opens or closes the menu.
- It must not start the Run action.
- When the menu is open, only the dropdown trigger receives the persistent
  `Dropdown Open` styling.
- The primary Run segment remains in its default or loading state.
- The open styling remains visible after the pointer leaves the trigger and
  until the menu closes.

The menu closes when:

- The user selects a menu item.
- The user activates the dropdown trigger again.
- The user presses `Escape`.
- The user clicks outside the menu.

When the menu is closed with `Escape`, focus returns to the dropdown trigger.

Hovering the Run segment can explain what the run will spend. Pass `cost` and
the tooltip appears above the segment; omit it and there is no tooltip.

      <td><code>cost=&#123;2950&#125;</code></td>

    </tr>
  </tbody>

See **AI New › Cost Tooltip › Spec** for the tooltip's own rules and for how
tooltips are applied across the system.

Rules:

- The tooltip belongs to the primary segment only. Hovering the dropdown
  trigger never shows it.
- It uses the shared Tooltip component — `--color-foreground` fill,
  `--text-xs` label, positioned `side="top"`.
- The cost is stated, never implied: do not replace the number with words such
  as "free" or "some credits".
- Keep the tooltip informational. It must not be the only place the price is
  shown before an expensive run.

### State rules

- Hover, pressed, focus, open, and loading states must not be applied to the
  shared wrapper.
- Each segment controls its own interactive states.
- `Dropdown Open` persists until the menu closes.
- Loading applies only to the primary segment.
- Disabled applies to the complete component and overrides all other states.
- Loading and Dropdown Open may exist at the same time.

---

## Loading behavior

When a Run action is in progress:

- Replace the `Run` label with one centered loader. No visible loading text.
- Keep the label in the DOM but hidden, so the segment keeps its exact width and
  the dropdown segment never moves.
- Apply the loading appearance only to the primary Run segment.
- Prevent the primary segment from accidentally starting a duplicate run unless
  concurrent runs are intentionally supported.
- Keep the dropdown trigger enabled and fully interactive.
- Do not apply loading opacity or disabled styling to the shared wrapper.
- Do not disable the dropdown because the primary action is running.

When the process completes or fails, return the primary segment to its default
state and communicate the result outside the button through the appropriate
success or error feedback.

---

## Disabled behavior

When the complete Run Button is disabled:

- Disable both the primary Run action and the dropdown trigger.
- Neither segment responds to pointer or keyboard activation.
- The dropdown menu cannot be opened.
- The component does not receive keyboard focus when native `disabled`
  attributes are used.
- Disabled styling applies consistently to both segments.

Loading and Disabled are different states. A loading primary action must not
make the enabled dropdown trigger appear disabled.

---

## Content guidelines

### Labels

Use:

- `Run` for the default state.
- `Running` as the accessible name while loading — the loader replaces the
  visible label, so the name comes from `aria-label`.
- `Open run options` as the accessible name of the icon-only dropdown trigger.

Keep labels:

- Short and action-oriented.
- Written in sentence case.
- Consistent across the product.
- Clear without relying on surrounding content.

Do not use:

- `Click here`
- `Submit` when the actual action is Run
- Ambiguous labels such as `More`
- A chevron without an accessible name

Do not add an ellipsis to `Run` — clicking it immediately starts the action, and
the loading state shows a loader rather than a text label.

## Accessibility

### Semantic structure

Use native HTML buttons for both interactive segments:

- Primary action: `<button type="button">`
- Dropdown trigger: `<button type="button">`

Do not give the shared wrapper `role="button"`.

The wrapper may use `role="group"` with an accessible label such as
`Run controls` when the relationship between the two buttons is not otherwise
clear.

### Accessible names

The primary button receives its accessible name from the visible `Run` label.
While loading the label is hidden and the name comes from `aria-label="Running"`.

The icon-only dropdown trigger must have an explicit accessible name:

```html
aria-label="Open run options"
```

The chevron icon inside the trigger is decorative and should be hidden from
assistive technologies:

```html
aria-hidden="true"
```

Expected screen-reader announcements include:

- `Run, button`
- `Running, button, busy`
- `Open run options, menu button, collapsed`
- `Open run options, menu button, expanded`

### Dropdown attributes

Apply the following attributes only to the dropdown trigger:

```html
aria-haspopup="menu"
aria-expanded="false"
```

When the menu is open:

```html
aria-expanded="true"
```

`aria-controls` may reference the menu ID when a stable relationship is
available.

Do not use `aria-pressed` to communicate the open state. `aria-expanded` is the
correct property for a button that opens and closes a menu.

If the dropdown contains a list of commands:

- The menu container uses `role="menu"`.
- Each actionable option uses `role="menuitem"`.
- The menu has an accessible name or is associated with the dropdown trigger.

If the dropdown contains form controls or complex content, do not use
`role="menu"`. Use a Popover or Dialog with native controls instead.

### Loading announcements

During loading:

- Set `aria-busy="true"` on the primary button or the related execution region.
- Hide the decorative loader from the accessibility tree.
- Use one polite status mechanism, such as `role="status"`, to announce
  meaningful changes such as `Run started`, `Run completed`, or `Run failed`.
- Avoid announcing the same loading message through multiple live regions.
- Keep keyboard focus stable when the button enters the loading state.

If the primary action cannot be activated again while loading, expose it as
unavailable and suppress additional activation without disabling the dropdown
trigger.

### Disabled semantics

When the entire component is disabled, apply the native `disabled` attribute to
both buttons.

If `aria-disabled="true"` is used instead, the implementation must manually
prevent pointer and keyboard activation because ARIA does not disable behavior
by itself.

Focus must never move between the primary button and dropdown trigger using

order.

### Focus appearance

- Each segment must have its own visible focus indicator.
- The focus indicator must identify which segment currently has focus.
- Do not apply one focus ring around the complete Split button.
- Do not remove the browser focus indicator unless it is replaced with an
  accessible custom indicator.
- Ensure the wrapper does not clip the focus ring.
- Opening the menu must require activation; receiving focus alone must not open
  it.

### Contrast

- Button text must have a contrast ratio of at least `4.5:1` against its
  background.
- The chevron, meaningful boundaries, open-state indicators, and custom focus
  indicators must have at least `3:1` contrast against adjacent colors.
- Hover or open styling must not reduce the contrast of the label or icon.
- Disabled controls are exempt from WCAG contrast requirements, but they should
  remain identifiable whenever possible.

### Target size

- Each button segment is a separate pointer target.
- Each segment must provide a target area of at least `24 × 24 CSS pixels`.
- For touch-first interfaces, aim for a target area of approximately `44 × 44`
  or `48 × 48` pixels.
- The visual divider must not reduce the interactive target size.

---

## Responsive behavior

- Keep the primary and dropdown segments attached at every viewport size.
- Do not allow the two segments to wrap onto separate lines.
- Preserve the minimum target size for each segment.
- Keep the menu within the viewport and reposition it when there is insufficient
  space.
- Mirror segment placement, border radii, and menu alignment for right-to-left
  layouts.

## Acceptance criteria

The component is complete when:

- Single and Split variants have clearly defined use cases.
- The Split variant uses two independent native buttons.
- Each segment has an independent interactive state.
- Dropdown Open styling affects only the dropdown trigger.
- Loading affects only the primary Run segment.
- The loader replaces the label without resizing the segment, and the button keeps an accessible name.
- The dropdown remains enabled during loading.
- Disabled affects both segments.
- Both segments can be reached and operated with a keyboard.
- Accessible names, roles, values, and expanded states are correctly exposed.
- Focus remains visible and is never clipped.
- The component meets WCAG 2.2 AA contrast and target-size requirements.
